# Phase 1 storage migration and recovery

Stop all old workers before upgrading. Do not share SQLite across hosts, network filesystems or mixed application versions. This release remains a single-host, single-worker application.

Before starting the new version, create consistent backups of the inbox and any local-session SQLite databases using `python manage_inbox.py --database PATH backup --output NEW_BACKUP_PATH`. The tool uses SQLite backup, includes committed WAL contents and checks integrity. Also copy the original local JSON files and record the Astra collection/HMAC-key configuration securely. Do not copy only the main SQLite file while writers are running.

Inbox migration runs transactionally at initialization. Legacy six-column inbox rows are retained. Schema version 2 adds sender/claim token/lease expiry/error metadata and outgoing intent, delivery-event, reminder and operator-review tables. Legacy `processing` rows become `review`, because a previous worker may already have acted. Startup never reclaims an unexpired processing lease. Expired claims become `review`; any sending outcome becomes `uncertain`. The migration refuses a future schema version. Session document fields remain compatible with the original Astra model.

The explicitly enabled development local-memory API now uses `LOCAL_MEMORY_PATH` plus `.sqlite3`. It imports the original JSON once under a transaction and retains the JSON untouched. A metadata marker prevents erased sessions being resurrected on reopening. Corrupt/oversized imports fail closed. Simulator storage has its own configured path. Production still requires Astra and rejects this local fallback.

Use `python manage_inbox.py --database PATH summary` to see counts/review metadata without message bodies. Stop the worker that owned a quarantined job and review provider/merchant outcomes before resolving it; an old in-flight database/network operation must not race the next conversation turn. Then resolve a quarantined job with `resolve --id JOB_ID --outcome already_processed|abandoned --reason "operator review explanation"`. This records an audit decision and releases later jobs for that sender. It does not resend, mark an uncertain external delivery successful, or rerun tools. Uncertain outgoing payloads and IDs remain available in the protected local database for investigation.

Successful raw inbound/outgoing payloads are cleared after seven days; incoming deduplication tombstones remain. Failed/uncertain records require operator handling. Full account erasure, physical Astra TTL, backup expiry, retention tooling and fleet-wide monitoring remain production qualification work, not claims made by Phase 1.

Rollback: stop new workers; back up their current data for reconciliation. Restore the pre-upgrade source/data into a separate private folder, preserving the upgraded database for review. Do not run the old worker against version 2 queues or replay uncertain jobs. The original source has known vulnerabilities: any baseline rollback must stay offline/loopback with webhooks and simulator exposure disabled. Restore production service only with a verified repaired build. Never rotate the HMAC key as an incidental rollback: it determines existing Astra document keys. No destructive down-migration is provided.
